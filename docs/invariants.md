# ReturnFlow 正确性不变量

本文定义业务系统的验收边界，不是教学题库。状态、权限、证据和外部效果的权威实现位于后端及其测试；以下断言必须按实际代码与运行环境核验。

## 1. 租户及权限

- ReturnCase、Approval、RefundAttempt 归属明确的 Organization。
- 用户查询必须按组织隔离；跨租户请求不能泄露目标对象是否存在。
- UI 可见操作不是授权依据；服务端的角色、租户、资源、版本及状态检查是实际门禁。
- 高额退款要求两个不同的 finance 用户批准**相同金额**。第一个批准即使不改变业务状态，也必须推进版本。

## 2. 状态机和并发

- 业务状态遵守显式状态转换；CLOSED、REJECTED 为终态。
- 涉及共享业务事实的更新以同一事务内的版本条件和数据库约束防止并发竞争。
- 两个请求基于同一旧版本作出冲突修改时，至多一个获得该版本的有效推进。
- 申请金额和批准金额满足业务约束；金额应使用无浮点误差的表示。

## 3. 幂等和事件

- 幂等身份按 (organization_id, scope, key) 限定。
- 相同键与相同内容可以复用已有结果；相同键与不同内容必须报告冲突。
- 并发重复请求通过持久化唯一约束等措施收敛，不能降级为非预期的服务端异常。
- Webhook 事件身份唯一；重复一致内容可安全处理，身份相同而内容冲突必须拒绝。

## 4. 外部退款与回读

- Outbox 中的计划动作不等于外部效果已发生。
- HTTP 超时或 ACK 丢失不能直接证明退款成功或失败。
- 外部效果可能已经发生时，UNKNOWN 不允许无依据地重新发出退款。
- Webhook 或支付方权威查询可提供退款证据；晚到的超时处理不得覆盖已经确立的 SUCCEEDED。
- 支付证据、退款业务状态、财务对账和最终结案必须分离。

## 5. 审计和证据范围

- 重要业务转换保留行动者、资源、动作和必要的审计信息。
- 单元测试、SQLite API 测试、PostgreSQL 并发测试、模拟支付异常、浏览器测试及本地 n8n 运行检查分别支持不同范围的主张。
- 模拟支付方结果不代表生产支付网络或真实财务合规；通过测试不推出所有外部风险已被覆盖。
