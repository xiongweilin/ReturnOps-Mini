# ReturnFlow 求职讲解稿

适用于 4–5 分钟的作品讲解。先从业务问题开始，再展示工作流和人工处理，不需要先介绍底层技术。

## 开场：业务问题

ReturnFlow 面向中小型电商的退货退款流程。一个申请要经过客服判断资格、仓库收货验货、财务审批，再到支付和对账。信息分散在不同岗位和工具里，重复录入会造成重复工单；更严重的是，退款请求超时并不代表支付没有发生，直接重试可能造成重复退款。

我做这个作品，是要把岗位交接和退款结果连成可操作的流程，同时让每个关键决定留在负责的业务人员手里。

## 两条 n8n 工作流

第一条是 **Return Intake**。客户退货事件进入 Webhook 后，工作流检查并整理申请，再交给 ReturnOps 建立工单。同一个事件重复送达时，会返回原来的工单；内容冲突或申请无效时会明确拒绝，不会重复建单。

第二条是 **Operations Digest**。它按日程或手动触发，从当前业务记录读取待办，再按客服、仓库和财务的职责整理摘要并发送到本地 Mailpit。它帮助每个岗位看到下一步该处理什么，不替任何人审批。

## 人工审批与岗位交接

普通流程依次经过客服审核、仓库收货与验货、财务批准退款和对账。高额退款还要由另一位财务人员对同一笔金额完成第二次审批。管理员可以查看演示状态，但不能越过这些业务步骤。

讲解时可展示待办如何从一个岗位交到下一个岗位，再展示高额退款在第二人审批前仍不能继续。重点是审批责任和流程状态对得上，而不是审批页面用了什么框架。

## 结果未知时如何处理

演示的关键异常是：Fake Payment 已经保存退款，但响应延迟到客户端超时。此时系统显示“结果未知”，保留一次派发记录，也不自动重试。财务人员查询支付方的权威记录，确认退款结果后再完成对账和结案。

这体现了一个业务规则：超时只说明系统没有及时收到回复，不能据此断定支付失败。先查清事实，再恢复流程，可以避免重复退款。

## 演示顺序

1. 从运营总览说明当前有哪些申请和岗位待办。
2. 展示 Intake 收到申请、重复事件仍落到同一工单。
3. 通过客服、仓库和财务完成一笔普通退款；再说明高额退款需要第二位财务人员批准。
4. 运行 UNKNOWN 场景，展示暂停自动重试、查询支付方结果、对账并结案。
5. 展示 Digest 工作流和 Mailpit 收件结果，说明通知来自真实待办数据。

## 面试追问时的简短回答

- **为什么用 n8n？** 用它连接外部事件和通知；业务状态、权限和退款审批仍由业务系统执行，因此重放工作流不会绕过审批。
- **如何防止重复退款？** 重复申请用同一事件标识归并到原工单；支付结果未知时先暂停，并查询支付方事实，不盲目重新派发。
- **这证明了什么？** 它证明仓库范围内的合成业务流程可重复运行，并覆盖正常审批、重复接单和退款结果未知的恢复路径。
- **它还没有证明什么？** 没有接入真实商户、真实支付或外发邮件，也没有真实客户试用数据，因此不声称已经节省了工时或降低了差错率。
